# Android → desktop parity contract

This is the implementation checklist for the Avalonia desktop port. Android source plus a physical TECNO CH6i capture on 2026-09-30 define the current reference. Screenshots contain account identity and remain local. Desktop visuals and native Windows behavior require separate evidence; source parity alone does not close a row.

## Current implementation checkpoint

- Scope update (2026-09-30): the user requested only important, local repairs. The active work is atlas/Home appearance, one-window adaptive layout, and Telegram code→import recovery. The broader gaps below are reference notes, not a mandate to expand this delivery.
- The table below records the **starting desktop baseline**. The working tree now has an adaptive bottom navigation on compact windows, a source-matched Android atlas embedded through `NativeWebView`, restructured Home/Routes/Profile/Settings, automatic import after Telegram code verification, recoverable account states, and direct support messaging. Keep the baseline entries until their acceptance evidence is complete.
- Linux Release build succeeds with zero warnings/errors. Dynamic resize across 1240×820 → 520×420 → 1240×820 was visually checked on all four destinations. Embedded atlas was separately checked for Ufa↔Amsterdam arc, country labels, drag, node tap, keyboard zoom, reduced motion, and empty node availability. Full-app atlas state and modal keyboard QA remain in progress.
- Active Auto outbound and traffic motion remain disabled until the Windows service provides actual route and byte data. Source code currently cannot prove either from egress IP or a connected flag.
- Native Windows WebView2, real Telegram code import, VPN tunnel/egress, account mutations, and payments have not been exercised. These rows remain open.

## State and action gaps to close

1. **P1, pairing:** Android's linked-account Reconnect starts a new username/code flow. Desktop currently calls setup with `RestoreExistingSession=true` (`MainWindow.ProfileParity.cs:177-225`, `MainWindow.PortFlows.cs:27-73`, `SetupWindow.cs:240-288`). Force pairing only for this action.
2. **P1, code completion:** Android code verification continues into subscription import and Home (`SetupActivity.kt:303-509,139-211`). Desktop stops at Success and waits for Import (`SetupWindow.cs:434-522,942-975,583-610`). Continue automatically with bounded progress and recovery.
3. **P1, profile error:** Android shows a specific loading/error/retry card (`ProfileFlows.kt:293-357`). Desktop infers “no active subscription” from absent data even during load errors (`MainWindow.axaml.cs:1001-1020`). Separate unknown, loading, error, and confirmed none.
4. **P2, profile disclosure:** Android groups Devices/Sessions and Help/Documents behind explicit expand controls (`ProfileFlows.kt:92-189,256-287`). Desktop exposes all management rows at once (`MainWindow.axaml.cs:985-1120`).
5. **P2, support:** Android sends normal messages directly and asks before closing a ticket (`ProfileFlows.kt:737-908`). Desktop confirms every send (`SupportWindow.axaml.cs:367-422`). A lifetime-plan support action also jumps straight to Telegram (`MainWindow.axaml.cs:2198-2250`).
6. **P2, route availability:** Android quick choices come from the available route catalog (`TopLevelPages.kt:255-272`); desktop renders placeholder Auto/RU-DE even when signed out (`MainWindow.axaml.cs:751-952`).
7. **P1, service loss:** Windows keeps the old connected snapshot when its service pipe fails (`MainWindow.axaml.cs:2058-2065`), so Home can claim the tunnel remains connected. Android reconciles actual VPN/network state (`ConnectVpnService.kt:649-694`).
8. **P1, stop while connecting:** Windows disables its primary action during starting/checking (`MainWindow.axaml.cs:699-765`), although the service supports disconnect (`EngineController.cs:192-205`). Android offers Stop during startup (`MainActivity.kt:644-690`).
9. **P1/P2, truthful atlas state:** Windows infers Auto exit from egress IP country and animates whenever connected (`MainWindow.axaml.cs:497-502`). Android reads the active outbound from libbox (`ConnectVpnService.kt:549-605`) and gates traffic animation on observed bytes (`MainActivity.kt:1792-1818`). Service snapshot needs active outbound and byte counters before claiming parity.
10. **P1, diagnostics progress:** Android updates per-route latency, speed, retry, wait, and error states while a country probe runs (`TopLevelPages.kt:483-586`). Windows service returns one final `probe_complete` (`EngineController.cs:330-399`), so desktop cannot show the intermediate rows; add a streamed progress contract.
11. **P1, diagnostics lifecycle:** Android stops foreground probes when leaving Routes (`TopLevelPages.kt:222-228`); desktop currently keeps queued/active country probes after navigation (`MainWindow.axaml.cs:175-213`). Preserve explicit all-routes diagnostics semantics if they differ.
12. **P2, diagnostics choice:** Android summarizes best/average/worst and per-route grade, and AWG has Select versus Connect & measure (`TopLevelPages.kt:355-366,590-725`). Desktop has only final raw results and automatic AWG probing on expansion.
13. **P2, payment/support choice:** Android lifetime/unlimited plans offer in-app support or Telegram (`ProfileFlows.kt:598-628`); desktop jumps directly to Telegram (`MainWindow.axaml.cs:2597-2619`).
14. **P2, payment recovery:** Android keeps quote parameters on failure and offers retry (`ProfileFlows.kt:659-685`); desktop shows a generic modal and forces the plan flow to restart (`MainWindow.axaml.cs:2727-2801`). Payment-status errors should retain server detail (`MainWindow.axaml.cs:2804-2850`).
15. **P2, traffic summary:** Android displays total transferred bytes even on unlimited quota (`ProfileFlows.kt:334-342`); desktop only shows traffic when the limit is positive (`MainWindow.axaml.cs:3447-3463`).

## Validation rule

Mark a row complete only after its source contract, desktop behavior, and visual/device evidence agree. Linux preview and a successful .NET build do not prove Windows WebView2, Telegram pairing, or tunnel behavior. Keep platform-specific controls where Windows requires them; reproduce the Android user's intent and interaction semantics.
