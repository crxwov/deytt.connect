# Android → desktop parity contract

This is the implementation checklist for the Avalonia desktop port. Android source plus a physical TECNO CH6i capture on 2026-09-30 define the current reference. Screenshots contain account identity and remain local. Desktop visuals and native Windows behavior require separate evidence; source parity alone does not close a row.

## Android visual update — 2026-10-24 (0.11.49)

The Android redesign now follows the Windows v0.11.47 HTML stages (09e3575). The older desktop-port checklist below is historical; its Android Home order is superseded by this section.

- Typography: Unbounded for display headings and the wordmark, Inter Tight for controls/body/map labels, JetBrains Mono for route metadata. Fonts remain bundled and offline.
- Palette: dark navy native background `#080D17`, translucent slate surfaces, blue action `#1686F4` → `#1170DC`, cyan `#29B9F0`, mint `#39E8BD`. Globe shading uses `#34465B` / `#243345` / `#111B29`, gray filled land, subdued country borders and truthful route annotations.
- Home: full globe, left-aligned flag/destination/protocol, one connection action, equal-width latency/speed columns and full-width refresh. Numeric measurements retain their emphasis; status messages use smaller text. Normal idle/connected notices are omitted; progress/errors remain. The former route-details button/strip is removed.
- Shell: one continuous starfield covers the whole window, including system insets and the frameless brand/avatar header. One persistent `RouteGlobeView` moves between Home and a background behind transparent Routes/Profile/Settings. Secondary pages apply the Windows blur/dim treatment; the header and capsule dock stay outside `ViewPager2`.
- Android overview mode gently pans toward the selected/active route at full-globe scale, with zoom bounded to 0.82–1.2. Repeated telemetry preserves manual framing. Map annotations use a compact 0.9 scale. `ProtocolActivity` retains its existing route-focus camera; the Windows mouse-wheel interaction profile is separate. Map taps, two-finger gestures and single-finger page navigation remain available.
- Motion: 120/140ms touch press response, 210ms interruptible profile accordions, subtle pager depth/opacity and a dock highlight driven continuously by page offset. Its 20dp radius follows the 28dp outer capsule with an 8dp inset. Navigation and accordions use system-respecting haptics. App/system reduced-motion settings suppress transforms and snap the camera via a deferred host bridge.
- Reuse the Windows land polygon decoder **and** painter together. The Android renderer centers at `width/2,height/2`; it has no Windows `centerX/centerY` fields. Atlas status overlays must not intercept pointer events, and native atmosphere drawing must stay inside drawable bounds.

Physical offline QA passed on Android13 / TECNO CH6i using the isolated `.qa` package. The existing `OpenFluxVisibilityInstrumentation` checks route selection without connecting, all four settled pages, continuous sky, balanced metrics/full-width refresh, compact long-status text, no route-details control, real bounded two-pointer zoom without paging, reset, and Home → Routes swipe. It also checks rapid accordion reversal, reduced-motion page/camera state, drawable bounds and loaded land polygons. Device vibrator diagnostics recorded TOUCH effects for the QA app. Screenshots are written to the QA app cache under `main-pager-visual-qa`; a local screen recording preserves motion evidence.

Build the isolated app/test with `-PisolatedQa=true -PqaRunner=space.deytt.connect.OpenFluxVisibilityInstrumentation`, grant its notification permission on Android13+, and run that instrumentation on `.qa.test`. It clears only the isolated fixture account/session data and must never target the production package. Live Telegram authentication, payments, real VPN traffic and production update installation need separate acceptance; this UI check does not claim them.

## State and action gaps to close

1. **P1, pairing:** Android's linked-account Reconnect starts a new username/code flow. Desktop currently calls setup with `RestoreExistingSession=true` (`MainWindow.ProfileParity.cs:177-225`, `MainWindow.PortFlows.cs:27-73`, `SetupWindow.cs:240-288`). Force pairing only for this action.
2. **Source parity added; native flow proof pending, code completion:** Android code verification continues into subscription import and Home (`SetupActivity.kt:303-509,139-211`). Desktop now calls `CompleteImportAsync(automatic: true)` after successful code verification (`SetupWindow.cs:404-405,492-496`); verify the full code-to-ready flow and bounded recovery on native Windows.
3. **Resolved in source; native visual proof pending, profile error:** Android shows a specific loading/error/retry card (`ProfileFlows.kt:293-357`). Desktop now separates loading, error with adjacent retry, confirmed inactive only after a successful loaded snapshot, and signed-out Telegram prompt. QA signed-out screenshot confirms the prompt; verify error rendering/retry on native Windows.
4. **P2, profile disclosure:** Android groups Devices/Sessions and Help/Documents behind explicit expand controls (`ProfileFlows.kt:92-189,256-287`). Desktop exposes all management rows at once (`MainWindow.axaml.cs:985-1120`).
5. **P2, support:** Android sends normal messages directly and asks before closing a ticket (`ProfileFlows.kt:737-908`). Desktop confirms every send (`SupportWindow.axaml.cs:367-422`). A lifetime-plan support action also jumps straight to Telegram (`MainWindow.axaml.cs:2198-2250`).
6. **P2, route availability:** Android quick choices come from the available route catalog (`TopLevelPages.kt:255-272`); desktop renders placeholder Auto/RU-DE even when signed out (`MainWindow.axaml.cs:751-952`).
7. **P1, tunnel health:** Startup HTTPS is verified once, but later monitoring is process-only; a silent tunnel loss can leave Home green/connected. Service state still lacks active outbound and live byte counters needed for truthful route/traffic display. A worker is implementing tunnel-health changes; keep this gap open until tests and user-visible failure recovery pass. Android reconciles actual VPN/network state (`ConnectVpnService.kt:649-694`).
8. **Resolved in source; native interaction proof pending, stop while connecting:** Windows exposes cancellation during starting/checking and serializes disconnect after any pending connect (`MainWindow.axaml.cs:2347-2377`). Android offers Stop during startup (`MainActivity.kt:644-690`). Verify the transition and recovery on native Windows.
9. **P1/P2, truthful atlas state:** Windows infers Auto exit from egress IP country and animates whenever connected (`MainWindow.axaml.cs:497-502`). Android reads the active outbound from libbox (`ConnectVpnService.kt:549-605`) and gates traffic animation on observed bytes (`MainActivity.kt:1792-1818`). Service snapshot needs active outbound and byte counters before claiming parity; covered by the pending tunnel-health work above.
10. **P1, diagnostics progress:** Android updates per-route latency, speed, retry, wait, and error states while a country probe runs (`TopLevelPages.kt:483-586`). 11. **Resolved in source, diagnostics lifecycle:** Android stops foreground probes when leaving Routes (`TopLevelPages.kt:222-228`); desktop now clears queued work and cancels the active country probe on navigation (`MainWindow.axaml.cs:253`). Native interaction remains unverified.

## Validation rule

Mark a row complete only after its source contract, desktop behavior, and visual/device evidence agree. Linux preview and a successful .NET build do not prove Windows WebView2, Telegram pairing, or tunnel behavior. Keep platform-specific controls where Windows requires them; reproduce the Android user's intent and interaction semantics.
